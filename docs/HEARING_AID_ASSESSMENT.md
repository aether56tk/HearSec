# HearSec Hearing-Aid Assessment\n\nHearSec assesses a hearing aid from documented, authorized evidence. A serial/research ID identifies the assessment; it is not a security test by itself.\n\n## Assessment pipeline\n1. Identify the device and authorized scope.\n2. Collect permitted evidence from the device ecosystem.\n3. Record evidence provenance.\n4. Assess the security domains.\n5. Map evidence to controls and findings.\n6. Calculate risk only when likelihood and impact are supported.\n7. Leave unknown or unassessed items as not_assessed / not_rated.\n8. Generate a reproducible report.\n\n## Evidence sources\n- Manufacturer documentation\n- Clinical/fitting software export\n- Companion-app export\n- Authorized SDK/API\n- Browser-observed device/service metadata\n- Laboratory observations on an owned/authorized device\n- Configuration export\n- Security test records\n\nHearSec does not require every source. Evidence that is unavailable remains unavailable.\n\n## What is assessed\n\n### 1. Device identity\n- Manufacturer, model, firmware, de-identified serial/research ID, hardware/device type\n\n### 2. Connectivity\n- Bluetooth/BLE or other documented connectivity\n- Hearing aid to phone path\n- Phone to cloud path where applicable\n- Connectivity evidence and provenance\n\n### 3. Pairing and authentication\n- Pairing requirements\n- Re-pairing behaviour\n- Authentication controls\n- Access restrictions\n- Unknown items remain unassessed\n\n### 4. Services and interfaces\n- Documented or authorized-observed interfaces\n- Exposed service metadata\n- Interface purpose\n- Whether access is restricted\n- No bypass or exploitation is required\n\n### 5. Firmware and updates\n- Firmware version\n- Update mechanism\n- Update authorization\n- Integrity/signing information when documented\n- Rollback/update observations when authorized\n\n### 6. Companion application\n- App version and platform\n- Permissions relevant to hearing technology\n- Local data handling\n- Authentication/session observations\n- Evidence from authorized app exports or testing\n\n### 7. Cloud services\n- Documented cloud dependency\n- Data categories transferred\n- Authentication/session controls when observable through authorized evidence\n- Security/privacy documentation\n- Do not infer undocumented cloud behaviour\n\n### 8. Privacy\n- Data categories\n- Device/configuration data\n- Usage/telemetry data\n- Account identifiers\n- Clinical information where applicable\n- Storage/transmission protections when evidenced\n- De-identification/data-handling controls\n\n### 9. Clinical software\n- Fitting/clinical software involved\n- Exported device data\n- Access control\n- Update/configuration workflows\n- Evidence provenance\n\n### 10. Access control and logging\n- User/clinician roles\n- Administrative access\n- Authentication\n- Audit/logging evidence\n- Monitoring evidence\n\n### 11. Resilience\n- Safe behaviour during disconnects\n- Update failure handling\n- Configuration recovery\n- Availability observations\n- Only record what was actually observed or documented\n\n### 12. Physical/service boundary\n- Physical service interfaces\n- Service/debug documentation if legitimately available\n- Tamper/service controls where documented\n- No unauthorized hardware modification is required\n\n## Risk rule\nRisk score = likelihood × impact.\nIf either input is unknown, not assessed, or otherwise unsupported, the result is not_rated.\nA missing observation is not automatically a vulnerability.\n\n## Minimum evidence record\n- unique evidence ID\n- evidence type\n- description\n- source\n- observation time where relevant\n- method\n- provenance\n- reproducibility status where known\n\n## Output\nA completed assessment produces:\n\ndevice identity → evidence → domains → controls → findings → risk → report\n\nThe final report states the assessment scope and limitations and does not claim that a third-party hearing aid is secure or insecure beyond the evidence actually documented.
